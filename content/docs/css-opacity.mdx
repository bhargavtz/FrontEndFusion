# Opacity

`opacity` takes a number from `0` to `1`, where `0` is fully transparent and `1` is fully opaque. It applies to the element as a whole — background, border, text, and every descendant — which is both its strength and its main limitation.

## What the property actually does

The browser renders the element and its subtree into an offscreen layer, then composites that layer onto the page with the requested transparency. As a consequence, a child cannot be more opaque than its parent. If a card has `opacity: .5`, a `color: #000` heading inside it will visually read as grey, no matter what colour you declare.

That behaviour is useful for disabled states, hover fades, and modal backdrops, where fading the group is the intent. It is wrong for a translucent panel that needs crisp text on top. In that case, use an alpha colour on the background — `rgba(255, 255, 255, .6)` or `hsl(0 0% 100% / .6)` — so the text keeps full contrast while the panel lets the backdrop through.

Opacity is also animatable and cheap to composite in modern browsers, which makes it a good choice for transitions. Animating `opacity` is far less expensive than animating `background-color`, because it can be handled by the compositor.

## Stacking and side effects

Any value below `1` creates a stacking context. That means `z-index` on descendants is contained within the faded element, and a child can never paint above a sibling of its faded ancestor, no matter how large its `z-index`. This is a common cause of "my tooltip is behind the header" when a parent has a fade applied.

Opacity also affects hit testing and rendering of shadows: a box shadow belongs to the element, so it fades with it. For partially transparent text alone, prefer `color` with alpha, which leaves children unaffected.

Legacy Internet Explorer lacked `opacity` and needed the proprietary `filter: alpha(opacity=50)` alongside it. That syntax is dead; do not include it in new code.

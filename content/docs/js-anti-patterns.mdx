# Anti-patterns

An anti-pattern is a solution that looks reasonable but tends to create bugs or confusion. Learning to recognize them helps you both avoid writing them and clean them up when you inherit code. JavaScript's flexible syntax offers several ways to shoot yourself in the foot.

## Chained assignments in variable declarations

One classic trap is chaining assignments inside a single declaration, for example writing `var a = b = c = 0;`. It looks like it declares three locals, but only `a` is actually declared. The names `b` and `c` become assignments to whatever `b` and `c` resolve to, which in non-strict code means properties on the global object. The result is accidental shared state that any part of the page can read or overwrite.

The problem is worse with objects. Chaining `var first = second = {};` gives both names the *same* object, so mutating one silently changes the other. Declaring each variable explicitly avoids both issues: `let a = 0, b = 0, c = 0;` makes the intent obvious and keeps everything in local scope.

Strict mode turns the chained version into a `ReferenceError` because assigning to an undeclared name is forbidden. That is a good thing, though relying on strict mode alone is not a substitute for clear declarations.

## Why clarity beats cleverness

Chained declarations save a few keystrokes but cost a lot of readability. A reader has to remember which names were declared and which leaked. Other common anti-patterns share this theme: comparing with loose equality, using `eval` for data, ignoring return values from array methods that are non-mutating, and adding properties to built-in prototypes. In each case, a slightly longer but explicit version is almost always better.

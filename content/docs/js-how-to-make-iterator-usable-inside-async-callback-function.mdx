# How to make iterator usable inside async callback function

A classic JavaScript trap appears when a loop schedules an asynchronous callback that uses the loop counter. Functions declared with `var` are scoped to the whole function, not to each iteration, so every delayed callback closes over the same variable. By the time the timers run, the loop has finished and the counter holds its final value, producing a row of identical results instead of distinct ones.

## The erroneous version

Consider a loop that uses `var i` and a `setTimeout` that prints `i`. Because there is only one `i`, all callbacks read the value left after the last iteration. The same bug shows up with `for ... in` or when an index is read from an outer variable inside a promise callback or request handler. The symptom is always the same: the callback sees the state at execution time, not at scheduling time.

## The correct version

The simplest fix is to declare the counter with `let`, which creates a fresh binding per iteration so each callback captures its own value. In older code, an immediately invoked function expression achieves the same effect by passing the current value in as an argument. A third option is to make a copy with a named constant inside the loop body. All three approaches freeze the value the callback will see.

The demo runs both versions side by side. The "buggy" loop uses `var` and every timer prints the same number; the "fixed" loop uses `let` and prints the expected sequence.

# Same Origin Policy & Cross-Origin Communication

Browsers isolate documents by **origin**, the combination of scheme, host, and port. The same-origin policy stops a script on one origin from reading the content of a document on another. Without it, a hostile page could read your mail or bank data simply by opening it in an iframe.

## Safe cross-origin communication with messages

The supported way to talk between origins is `window.postMessage()`. The sender passes a message and a target origin; the receiving frame listens for the `message` event and inspects `event.origin` before trusting anything. Checking the origin is essential: accepting messages from `"*"` means any page can send you data. A careful receiver also validates the shape of `event.data`, because a legitimate origin might still be compromised.

A typical handler looks like a small gate: ignore messages whose origin is not on an allowlist, ignore unknown message types, and only then act. Replies are sent back with `event.source.postMessage(...)`, using the exact origin that was received rather than a wildcard.

## Ways around the restriction (and their trade-offs)

Older techniques such as JSONP work by loading a script tag from another domain, but they execute remote code and cannot report errors cleanly. Server-side proxies move the cross-origin request to your backend, which avoids browser limits but adds infrastructure. CORS is the standard mechanism for letting one origin read another's resources: the server opts in with an `Access-Control-Allow-Origin` header. Note that a simple `fetch` to another origin is fine to *send*; CORS governs whether the response may be *read*.

The demo simulates two frames on different origins. A mock message bus delivers payloads, and the receiver enforces an allowlist. Try sending from an untrusted origin to see the message rejected.

      function deliver(origin, data) {
        var event = { origin: origin, data: data };
